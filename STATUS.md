# Project status

Last updated: 2026-11-02 (project lives at /data/hdrive/XPPAUT-Web)

**Live site:** https://zetaone.github.io/XPPAUT-Web/ (repo
https://github.com/ZetaOne/XPPAUT-Web, public, GPL-2.0-or-later). Every push
to `master` rebuilds and redeploys via `.github/workflows/pages.yml`
(~1.5 min). Commit/push only when the user asks.

## Goal

Port XPPAUT to run as a web application in the user's browser, keeping the
original desktop UI as close as possible, and letting users download plots,
.ode files and all data XPP creates. Based on the "Idea 1: Web port"
project at https://sites.pitt.edu/~phase/bard/bardware/xpp/gsoc_ideas.html.

## Chosen approach (A)

Compile the real XPPAUT C source to WebAssembly with Emscripten and
reimplement the Xlib functions it uses on an HTML canvas.

Why: XPP's UI uses raw Xlib with no toolkit (it draws its own buttons, menus
and dialogs), so a canvas Xlib layer reproduces the UI pixel for pixel, and
the numerics (ODE solvers, CVODE, AUTO) are reused unchanged. Files XPP
writes go to Emscripten's in-memory file system and can be offered as
downloads.

Rejected: a Linux VM in the browser (huge, slow), streaming from a server
(not in-browser), rewriting the UI in HTML (largest effort, drifts from the
original).

## Done

1. **Source imported.** Official XPPAUT 8.0 tarball in `xppaut/` (the
   GitHub repo is from 2016 and outdated). Provenance and checksum in
   `xppaut/UPSTREAM.md`. Desktop reference build: `scripts/build-native.sh`,
   `scripts/test-native.sh`.
2. **Builds without libX11.** `web/Makefile` builds against bundled
   X11 headers and placeholder Xlib functions (`web/xlib/xstub.c`, 69
   functions). Batch-mode output is byte-identical to the desktop build on
   all 144 example .ode files that produce output (gcc and clang).
3. **Compiles to WebAssembly and runs.** Emscripten 6.0.13 in `.emsdk/`.
   `make -C web wasm` gives `build/wasm/xppaut.wasm` (~1 MB) +
   `xppaut.mjs`; `scripts/xpp-wasm-node.mjs` runs it under Node.
   - vs a native build using musl's libm (`scripts/build-muslm-baseline.sh`):
     **byte-identical on all 144** examples.
   - vs the glibc desktop build: 129 identical, 15 differ only from last-digit
     libm rounding (exp/sin/pow) amplified in chaotic/stiff/adaptive-step
     runs. Accepted: desktop XPP on macOS differs from Linux the same way.

   Source fixes needed so far (11 files) are listed in the Patches table
   in `xppaut/UPSTREAM.md`.

4. **XPP's interface runs in the browser** (step 3, first working version).
   - `web/xlib/`: our own Xlib (the 69 functions XPP uses) on in-memory
     pixel buffers: window tree, compositing, GCs (copy/xor, dashes, line
     width), arcs, misc-fixed bitmap fonts (`fonts_data.c`, generated by
     `scripts/gen-fonts.py`), X colour names (`colors_data.c`), event queue
     with pointer/keyboard routing, implicit grabs, Enter/Leave.
   - `platform_native.c`: headless test harness, driven by a script
     (`XPPWEB_SCRIPT`; commands listed at the top of the file); screenshots
     as PPM. `XPPWEB_TRACE=1` logs drawing calls.
   - `platform_web.c` + `src/xpp.ts`: browser side. Asyncify lets XPP's
     blocking event loops wait; each X top-level window is a draggable,
     resizable panel with a canvas. Keys go to the last raised window.
   - `src/main.ts`: start screen (149 bundled examples or upload), a Files
     menu to download anything XPP wrote, XPP's text output log.
   - Verified in headless Chrome (`scripts/browser-test.mjs`): main window,
     keyboard (I G), menus by mouse, Initial Data window, editing a value
     and re-running, AUTO window with a steady-state continuation (Morris-
     Lecar S-curve with labelled special points).
   - Verified natively: Parameters, Equations, Data Viewer windows,
     nullclines, direction field, AUTO continuation.
   - Like the X server, a configure request that changes nothing sends no
     ConfigureNotify (XPP re-resizes windows from that handler; sending it
     looped forever when the Equations window opened).
   - Keys typed during an integration are discarded by XPP itself (its
     abort check reads them), as on the desktop.
5. **Pixel-identical to the desktop XPP**: 32 screenshots in 22 scenarios
   (`tests/gui/`), including 3D view, array plot, animation (pend.ani
   loaded and played), file selector, calculator, sliders, numerics and
   kinescope menus, singular points, Lorenz in 3D, data browser scrolling,
   Makewindow, Xi vs t, window fit. Scripts can set `# ode:` and `# files:`.
   `XPPWEB_NOWM=1` makes the harness a bare X server like Xvfb (top-level
   borders, exposure between top-levels), for these comparisons only.
   Known test-only artefact: in calc.txt the main window is not compared
   (it depends on top-levels overlapping without a window manager).
   `scripts/compare-gui.sh tests/gui/*.txt` runs each script on the real
   XPP (Xvfb + xdotool, `scripts/xref.py`) and on our Xlib (headless
   harness, `XPPWEB_NOWM=1`), and compares every shot. All 10 identical:
   main window, integrate, nullclines + direction field, File menu,
   Parameters, Equations, Data Viewer, Initial Data, AUTO window, AUTO run.
   `tests/xdraw/run.sh` draws a rasterisation test with real libX11 and
   ours: lines of every width/angle, polylines, dashes, XOR, text, filled
   and wide circles match exactly; only thin odd-size circles and partial
   thin arcs differ (XPP draws neither).
   X behaviours this needed: backgrounds (incl. tiled pixmaps) painted on
   map; Expose for areas revealed by raise/lower/unmap/move/border shrink
   (XPP switches menus with XRaiseWindow); XParseColor shifts hex digits;
   wide lines/arcs use the X polygon rule with pixel-centre coordinates;
   width 1 is a wide line.
   - Batch output still byte-identical on all 144 examples (wasm vs musl
     baseline) with Asyncify.

6. **Separate browser windows** (user's request): any XPP window can be
   popped out with ⧉ in its title bar; closing the browser window docks it
   back, and closing it in XPP closes the browser window. Toolbar option
   "New windows in separate browser windows" (remembered per browser)
   opens XPP's new windows that way; needs pop-ups allowed for the site.
   Input uses pointer events with capture and per-window coordinates, so
   everything works the same docked or popped out.

7. **Two WebAssembly builds**: `make -C web wasm` links the same objects
   twice. JSPI (`build/wasm-jspi`, 1.1 MB) runs at native speed in batch
   mode; Asyncify (`build/wasm`, 1.6 MB) works in every browser but is
   1.5-2.3x slower in batch. The page loads JSPI when
   `WebAssembly.Suspending` exists (`?engine=asyncify` forces the other).
   Both are byte-identical on all 144 batch examples
   (`XPPWEB_WASM=jspi` selects the build in `scripts/xpp-wasm-node.mjs`).
   Interactive run of kuramot100.ode (I G): native 6.9 s, browser JSPI
   8.8 s, browser Asyncify 10.5 s. `window.xpp.busy` tells tests when XPP
   is computing.

8. **Closable windows** (user's request): × on any window presses that
   window's own Close/Cancel/Quit/Done button (the Xlib layer remembers the
   text drawn in each window), so XPP runs its own close code; Makewindow
   graphs close via a small XPP patch handling WM_DELETE_WINDOW; × on the
   main window opens XPP's File/Quit "Are you sure?". Closing a popped-out
   browser window closes that XPP window (the main window docks back).
9. **Terminal output** (user's request): toolbar "Output" = Hidden / Side
   panel (resizable, Save, Clear) / Separate window; remembered; full
   history kept across modes (`src/terminal.ts`).
10. **Step 4, files**: Files panel lists XPP's working folder with sizes and
    times; click to download, "Download all (.zip)" (`src/zip.ts`), "Add
    files…" uploads into it; "Open .ode file…" accepts the model plus its
    data files; examples bring the .ani/.tab/.dat files they mention;
    ⤓ on each window saves a PNG; XPP's own PostScript and SVG export land
    in Files (verified: both render correctly); "Edit .ode" edits the model
    and restarts XPP with it (other files carried over).
    All verified in headless Chrome (scripts/browser-test.mjs has wclick,
    upload, downloads, popclick, popshot, popclose, targets).

11. **More of step 3 verified against the real XPP** (all identical, now
    37 shots in 25 scenarios): AUTO periodic orbits from the Hopf point
    (`autoper.txt`), Kinescope capture/playback (`kinescope.txt`), data
    browser Replace column via its dialogs (`datareplace.txt`; keys reach
    an XPP dialog while the pointer is over its text line, as on the
    desktop). File/Help opens the bundled HTML help in a browser tab
    (patched `xpp_hlp`, WebAssembly build only).
12. **Step 4 done**: $HOME is the working folder in the browser, so AUTO's
    output (.b/.d/.s) and data written by XPP appear in Files, and a
    .xpprc added via Files is read at startup.

13. **All 212 example models** in a grouped dropdown (XPP examples 149,
    AUTO test models 28, canonical 16, help-page examples 19; cuda/ left
    out: needs a GPU plug-in), each with its .ani/.tab/.dat files. URLs are
    `?ode=<group>/<file>` (bare names mean the main folder). A "Model"
    switcher in the toolbar restarts XPP with another example.
14. **Loading**: first visit downloads ~11 KB of page + 22 KB loader + the
    WebAssembly (JSPI 1.1 MB, 435 KB gzipped; Asyncify 1.6 MB, 570 KB).
    Measured: 0.3 s to XPP window on a fast connection, ~6.5-7 s on
    1.6 Mbit/s uncompressed (hosts that gzip: ~3 s). The page starts the
    download immediately with a progress bar ("Loading XPP… x of 1.1 MB",
    sizes from public/wasm/sizes.json) and hands the bytes to Emscripten
    via instantiateWasm, so the file is fetched exactly once.

15. **Published on GitHub Pages** (2026-11-03): repo ZetaOne/XPPAUT-Web;
    first deploy passed in 1m28s; live site verified in headless Chrome
    (load, integrate, nullclines). GitHub serves the wasm gzipped (437 KB).
    Actions annotations: actions/* v4/v5 run on deprecated Node 20 (forced
    to Node 24) - bump action versions when convenient.

## Open decisions

- Licence: XPPAUT is GPL v2, so the distributed web app must use a
  GPL-compatible licence.
- User-compiled C functions (`dlopen`, HAVEDLL) cannot work in the browser
  and are disabled.

## Setting up on a new machine

Needs git, gcc, make, Node and (for the desktop reference build) libX11
headers, e.g. `sudo apt install build-essential libx11-dev`.

```bash
npm install                  # web front end dependencies
scripts/build-native.sh      # desktop reference build
scripts/test-native.sh       # should print PASS
make -C web headless
scripts/compare-batch.sh build/headless-cc/xppaut   # 144 SAME, 9 NOOUT

source .emsdk/emsdk_env.sh           # Emscripten (install: scripts/setup-emsdk.sh)
make -C web wasm
scripts/build-muslm-baseline.sh
BASELINE=build/headless-muslm/xppaut scripts/compare-batch.sh scripts/xpp-wasm-node.mjs   # 144 SAME, 9 NOOUT

npm run build:wasm && npm run dev    # the web app at http://localhost:5173/?ode=lecar.ode
```
